# Project menu usability and design plan

## Scope and triage

Improve the Projects window's button contrast and visual hierarchy, keep search aligned with a saved project name, and prevent the shortcut used to open the window from entering the search field. This spans WPF, WinForms keyboard routing and desktop verification: **TRIAGE: MULTI-AGENT** under the repository guide. This document is the planning deliverable; implementation is a separate step.

## Findings

- `Source/Workspace/ZoneWorkspaceWindow.cs` builds the dark two-column window and uses Wpf.Ui secondary buttons; the reported two unreadable buttons must be identified visually in their actual enabled and disabled states before changing their style. Audit all secondary buttons using the same helper, including Undo/Redo, Jump, members, folder, export and member actions.
- `Save()` calls `IZoneCommands.Update`. `ZoneService.Update` trims the name, mutates the in-memory project and raises `Changed` even when persistence fails. A synchronous refresh can remove the selected row when the old search no longer matches, so setting the search only after the update without retaining the ID is insufficient.
- `OverviewManager.HandleZoneKey` invokes the window synchronously on P or Z, marking the WinForms key event handled only after the window opens. `ZoneUi.Show` immediately activates and focuses search. The exact native character delivery must be reproduced; setting `SuppressKeyPress` before invoking the callback is a candidate fix, but may not by itself suppress an already queued character after focus changes.

## Implementation checklist

1. **Establish the visual baseline.** Open the menu with an enabled project and inspect all button states at normal and narrow window sizes. Identify the two reported controls and the actual foreground/background resources from the rendered template; avoid assuming which buttons are affected. Capture a baseline for comparison.
2. **Make the dark theme legible and modern** in `ZoneWorkspaceWindow.cs`. Define coherent dark surface, text, border, accent and danger colors, using explicit locally scoped styles or Wpf.Ui theme resources that actually apply to rendered templates. Ensure normal, hover, pressed, keyboard-focus and disabled states are distinguishable. Target at least 4.5:1 text contrast for enabled normal-size text, and a visible focus indicator. Preserve legible disabled states. Refine spacing and typography, emphasize the selected project and primary Save action, group project settings separately from secondary and destructive actions, and show selected color with a non-color-only indicator. Keep existing labels, accessible names, functionality and keyboard navigation; ensure scrolling and layout work at the 700×460 minimum. Avoid unnecessary new dependencies or a wholesale redesign.
3. **Synchronize search after a successful save** in `ZoneWorkspaceWindow.Save()`. Capture the area ID and edited values before calling `Update`, because its synchronous `Changed` event may rebuild the tree. On successful persistence, set search to the canonical saved name obtained by ID (the service trims it), rebuild as needed, and restore the area selection by ID without stealing focus to the name editor. This applies even when the prior search was blank or matched a member. Preserve the existing query and failure message on validation or persistence failure; acknowledge that a persistence failure can still mutate the in-memory name. Do not report success when persistence fails. Preserve ancestor visibility for nested projects and avoid selecting a different duplicate name.
4. **Prevent shortcut text leakage** in `Source/Overlays/Overview/OverviewManager.Zones.cs` and, only if needed, `ZoneUi.cs`. Reproduce P and Z from the canvas, then consume the triggering key and character before showing/focusing the window; verify behavior through the WinForms/WPF boundary. If suppression alone fails, defer showing/focusing appropriately or use a narrowly scoped one-shot input guard tied to the initiating keystroke. Never strip a legitimate subsequent P or Z, alter existing search on opening, or affect toolbar/tray openings. Respect `Source/Overlays/Overview/AGENTS.md` and existing window-layer coordination.
5. **Add focused regression coverage** in `Tests/ZoneWorkspaceViewTests.cs` and the closest existing keyboard/integration tests. Cover a rename from an old-name filter, trimmed name, nested project and duplicate names, selection by ID, blank/member filters, invalid input and persistence failure. Exercise P and Z opening through real input where feasible, then type P/Z normally, including repeated opens, and check toolbar/tray access. Verify button appearance in rendered states with visual inspection rather than testing implementation-specific color constants alone.

## Verification and risks

- Implement in an isolated worktree following the repository workflow. Restore locked dependencies and build Release as described in `AGENTS.md`.
- Run the applicable filtered tests first through `Tools/Run-Tests.ps1` with `-NoPrompt`, then the standard Release suite through the same runner, which holds `Global\\CanvasWindowComposer.Tests`. Close Canvas cleanly before desktop testing. Run relevant overview keyboard, layer coordinator and toolbar tests as required by the subsystem guide.
- The keystroke and visual checks need an interactive Windows desktop and must not overlap other native/desktop tests. Check opening by P and Z, typing immediately afterward, changing existing search, and clicking Save; inspect focus, hover, disabled, high-DPI and minimum-size layout. Native desktop input may require an integration/manual check even if managed STA tests pass.
- No new unmanaged resources or background threads are planned. Input timing across WinForms and WPF and synchronous refresh during persistence are the primary regression risks. Avoid disturbing existing untracked plans and the current branch's unrelated changes.
